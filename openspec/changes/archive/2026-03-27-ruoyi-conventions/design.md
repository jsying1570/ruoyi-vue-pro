## Context

ruoyi-vue-pro 是一个基于 Spring Boot 3.x + MyBatis-Plus 的多模块企业级开发脚手架，包含系统管理、工作流、AI、商城、会员、支付等多个业务模块。项目采用模块化双层结构（API + BIZ），支持多租户和数据权限。

**当前状态：**
- 代码约定和架构模式分散在各处，新成员需要阅读大量代码才能理解
- 缺乏统一的规范文档，导致代码风格不一致
- 隐式的架构知识（如 DTO/DO 转换模式、权限标识符规范）未显式化

**约束：**
- 保持现有代码结构不变，仅补充文档
- 遵循已有的技术栈（Spring Boot 3.4.5, MyBatis-Plus, MapStruct）
- 兼容 Java 17+

## Goals / Non-Goals

**Goals:**
- 建立完整的项目规范文档体系
- 显式化架构知识和开发约定
- 为新成员提供清晰的上手指南
- 为代码审查提供标准依据

**Non-Goals:**
- 不修改现有代码结构
- 不引入新的框架或依赖
- 不重构现有模块

## Decisions

### 1. 文档组织结构

**决策**：采用 OpenSpec 规格驱动模式，将规范分为 proposal → design → specs → tasks 四个阶段

**理由**：
- OpenSpec 提供结构化的文档框架
- 便于后续变更管理和版本追踪
- 与项目现有的开发流程一致

**替代方案考虑**：
- 方案 A：单一 README.md - ❌ 无法覆盖复杂规范的各个维度
- 方案 B：Wiki 文档 - ❌ 不利于版本控制和代码同库管理

### 2. 规范覆盖范围

**决策**：覆盖 6 个核心维度（目录结构、模块组织、命名规范、API 接口、权限控制、代码分层）

**理由**：
- 这 6 个维度是日常开发最高频的决策点
- 覆盖从项目结构到具体编码的全链路
- 每个维度都有明确的实践指导价值

### 3. 规格说明粒度

**决策**：按能力（capability）组织规格，每个能力对应一个 `specs/<name>/spec.md`

**理由**：
- 能力是独立的关注点，便于理解和维护
- 符合 OpenSpec 的设计哲学
- 便于后续增量更新

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 规范与实际代码不一致 | 规范文档应描述现有实践，而非理想状态；定期审查更新 |
| 规范过于复杂，难以遵守 | 保持简洁，只覆盖高频决策点；提供示例代码 |
| 新成员不了解规范存在 | 在 README.md 添加显眼链接；新人入职引导包含规范阅读 |

## Migration Plan

无需迁移，纯文档变更。
